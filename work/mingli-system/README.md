# 命理系统报告模型与数据库

本目录用于沉淀一套可复用的命理综合研判系统。它的目标不是把报告写得更玄，而是让每一份报告都有统一的排盘校验、判断层级、置信度、专家质询和行动建议。

## 文件说明

- `report_model.md`：最高规格报告模型，定义完整输出结构、研判流程、质询标准和报告模板。
- `database_schema.json`：结构化数据库字段，用来保存出生资料、排盘结果、校验事件、专家质询、报告版本。
- `seed_records.json`：根据当前对话中已经提供的信息建立的种子人员资料，后续可继续补充时辰、事件和报告版本。
- `DATABASE.md`：SQLite 数据库初始化、表结构和当前入库内容说明。
- `PRECISION_READINESS.md`：高精度研判所需资料、验证和报告准入硬条件。
- `database/schema.sql`：数据库正式 SQL 表结构。
- `scripts/init_database.py`：初始化数据库、导入来源、理论、人物、案例和纠偏记录的脚本。
- `scripts/build_precision_foundation.py`：严格资料评分、模块准入和固定数据集划分。
- `scripts/report_gate.py`：在生成报告前阻止证据不足的精细结论。
- `scripts/rectify_birth_time.py`：双轨时辰纠偏，生成十二候选、隔离校时/留出事件并承接已知时辰盲测。
- `knowledge_base.json`：理论规则库，把核心理法拆成可调用、可冲突处理、可追溯的规则条目。
- `case_practice_records.json`：案例实践库，保存已出报告、命局模型、待验证事件、纠偏记录和复盘结论。
- `ten_million_validation_architecture.md`：1000万人公开样本验证工程架构。
- `validation_dataset_schema_v2.json`：大规模公开样本验证库字段结构。
- `public_validation_dataset_plan.md`：公开人物样本校验方案。
- `curation_strategy.md`：理论、案例、互联网资料的采集与入库策略。
- `personalization_engine.md`：千人千面报告生成引擎。
- `source_registry.json`：公开数据源和参考资料登记。
- `pipeline/`：公开人物样本采集、验证和规则评估管线契约。

## 使用原则

1. 每个人单独建档、单独出报告。
2. 农历资料必须标注是否闰月；未说明时按非闰月处理，并标注待确认。
3. 出生时辰必须区分北京时间、真太阳时、早子夜子和节气边界。
4. 无时辰盘不得伪装成完整盘，子女、晚年、健康细节和应期精度必须降级。
5. 四柱八字为主骨，调候、格局、十神、藏干、刑冲合害为核心分析层。
6. 紫微、奇门、梅花、六爻等只作适用场景补充，不能无条件混入出生盘。
7. 报告必须区分确定判断、推断判断、待校验判断。
8. 每份报告最后必须给出可执行行动方案。

## 数据库三层结构

### 1. 理论规则层

保存命理理法，不保存古籍长篇原文。每条规则都需要说明适用范围、优先级和冲突处理方式。

### 2. 案例实践层

保存每个人的出生资料、盘面、报告版本、命局标签、已知人生事件、后续反馈。案例用于参考，不直接套断。

### 3. 纠偏复盘层

当用户补充时辰、改生日、反馈某项不准、提供人生事件时，必须记录为修正项。后续同类命局要参考这些纠偏记录，避免重复犯错。

## 1000万人公开样本验证

大样本验证不直接等于高精度判断。系统把公开样本分成五层：

1. L0：公开人物索引。
2. L1：完整出生年月日，可排三柱。
3. L2：出生年月日加出生地。
4. L3：出生年月日时加出生地。
5. L4：出生资料完整，且至少有 5 个可核验人生事件。

只有 L3/L4 样本可用于验证时柱、大运应期、晚年、子女等精细模块。L0/L1 只用于宏观统计和筛选。

系统将“资料完整度”“管线合规率”和“结果命中率”分开记录。资料多、排盘成功或降级规则执行正确，都不能被表述为预测准确率；只有预先登记规则在未参与调参的验证集和测试集上优于基线，才可报告对应模块的统计表现。

## 以后出报告的标准流程

1. 录入出生资料。
2. 做排盘校验。
3. 建立命局骨架。
4. 判断五行气候、格局层次和用忌。
5. 分析性格、事业、财务、家庭、健康、阶段走势。
6. 加入专家质询，指出缺失与待确认项。
7. 形成最终报告和报告版本记录。
8. 把用户反馈写回案例库，用于后续纠偏。
