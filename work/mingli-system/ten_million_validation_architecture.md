# 1000万人公开样本验证工程 V1

## 一、为什么必须升级为工程体系

1000万人样本不是“多抓数据”，而是一个长期验证工程。它的核心价值不是数量本身，而是让命理报告具备：

1. 理论偏差识别能力。
2. 个体差异解释能力。
3. 案例回验能力。
4. 规则置信度更新能力。
5. 报告纠偏能力。

如果没有质量控制，1000万条错误数据只会让系统更自信地犯错。

## 二、总原则

### 1. 合法公开

优先使用开放结构化数据，例如 Wikidata 这类 CC0 数据源。普通个人隐私、非公开出生信息、医疗隐私、身份证明、住址、联系方式一律不采集。

### 2. 宁缺毋滥

每条样本必须有来源、字段精度、置信度。生日不完整、地点不明确、事件无来源的样本不能进入高精度验证集。

### 3. 分层验证

公开人物多半没有出生时辰，所以不能拿全部样本验证时柱和精确大运。必须分层：

- L0：姓名、出生年、职业等低精度样本。
- L1：完整出生年月日样本。
- L2：出生年月日 + 出生地样本。
- L3：出生年月日时 + 出生地样本。
- L4：出生资料完整 + 至少 5 个可核验人生事件样本。

### 4. 只让高精度样本影响精细判断

低精度样本只能参与宏观统计，不允许用于验证时柱、子女、晚年、具体应期。

### 5. 理论必须可被反证

每条规则都要允许被案例推翻或降权。不能为了维护理论而解释一切。

## 三、1000万人数据分层目标

### 第一层：1000万公开人物索引

目标：

- 建立公开人物基础索引。
- 字段包括姓名、唯一 ID、出生日期、出生地、职业、国籍、死亡日期、公开来源。

用途：

- 样本池。
- 去重。
- 宏观分布统计。
- 筛选高质量样本。

不用于：

- 精确命盘断事。
- 时柱验证。
- 具体应期验证。

### 第二层：100万可排三柱样本

目标：

- 出生年月日完整。
- 可以排年、月、日三柱。
- 可做日主、月令、职业、寿命段、时代分布验证。

用途：

- 检验月令、日主、职业倾向是否有统计偏差。
- 检验理论是否过度泛化。

### 第三层：10万事件样本

目标：

- 至少有 3 个明确年份事件。
- 事件类型包括事业、婚姻、迁移、奖项、争议、疾病、死亡、财富、职位变动等。

用途：

- 验证大运阶段主题。
- 验证冲合刑害的事件触发倾向。
- 建立规则偏差矩阵。

### 第四层：1万高精度样本

目标：

- 出生年月日时明确。
- 出生地明确。
- 至少 5 个可核验人生事件。

用途：

- 验证时柱。
- 验证起运。
- 验证细分六亲、晚年、子女、职业应期。

### 第五层：1000个深度案例

目标：

- 资料完整。
- 有年谱或传记级事件。
- 人生轨迹高度可复盘。

用途：

- 做人工精断复盘。
- 训练报告结构。
- 形成案例解释库。

## 四、数据管线

### 1. Source Intake

采集来源登记，不直接进入核心库。

字段：

- source_id
- source_name
- license
- source_url
- data_type
- refresh_cycle
- trust_level
- allowed_fields
- forbidden_fields

### 2. Identity Resolution

人物去重与身份合并。

需要处理：

- 同名人物
- 多语言名
- 艺名、字、号、别名
- 改名
- 同一人物多来源冲突

主键优先级：

1. Wikidata QID
2. VIAF / ISNI / Library of Congress 等公共标识
3. Wikipedia 页面 ID
4. 本地生成 ID

### 3. Birth Fact Normalization

出生资料标准化。

必须记录：

- 原始出生文本
- 标准化日期
- 日期精度：年 / 年月 / 年月日 / 年月日时
- 历法类型
- 是否推算
- 出生地层级
- 来源链接
- 冲突来源

### 4. Event Extraction

人生事件抽取。

事件不能只存一句“事业成功”，必须结构化：

- event_type
- event_date
- event_precision
- event_summary
- source_url
- evidence_quote_short
- confidence

注：引用必须短，避免保存长篇受版权保护文本。

### 5. Chart Calculation

命盘计算。

根据资料精度生成不同盘面：

- 三柱盘
- 四柱盘
- 真太阳时备选盘
- 起运备选
- 边界标记

### 6. Rule Evaluation

规则验证。

每条规则对每个案例输出：

- expected_pattern
- observed_event
- match_level
- mismatch_reason
- confidence
- reviewer

### 7. Bias Matrix

偏差矩阵。

统计：

- 哪些规则稳定。
- 哪些规则只在特定条件下成立。
- 哪些规则容易误导。
- 哪些报告段落最容易模板化。

### 8. Report Engine Feedback

将偏差矩阵反哺报告生成：

- 降低低置信规则权重。
- 增加“若……则……”条件句。
- 增加专家质询。
- 增加现实变量。
- 改写过度绝对化段落。

## 五、质量门槛

### 进入公开样本池

必须满足：

- 公开人物或历史人物。
- 至少一个合法来源。
- 至少有出生年。

### 进入三柱验证集

必须满足：

- 出生年月日完整。
- 日期来源明确。
- 可确认阳历或农历。

### 进入事件验证集

必须满足：

- 至少 3 个明确年份事件。
- 每个事件有来源。
- 事件类型可分类。

### 进入高精度验证集

必须满足：

- 出生年月日时完整。
- 出生地明确。
- 时区可确定。
- 至少 5 个可核验人生事件。

## 六、理论偏差处理

当样本显示理论偏差：

1. 不删除规则，先降置信度。
2. 增加适用条件。
3. 增加禁用条件。
4. 拆分规则。
5. 写入纠偏案例。
6. 更新报告模板。

示例：

- “财旺压身”不能一律写成钱财压力。需要分成身弱不任财、身有根能任财、财旺生官、财旺坏印、财在年月日时不同落点。
- “官杀重”不能一律写成压力。需要分成制度压力、职位权责、家庭规训、公共责任、竞争压力。
- “印旺”不能一律写成学习好。需要分成保护、依赖、文凭、经验、保守、贵人、母系资源。

## 七、报告纠偏闭环

每份报告生成前：

1. 读取命主盘面。
2. 检索相似命局。
3. 检索相似年龄、性别、地域、职业样本。
4. 检索相似案例的纠偏记录。
5. 生成稳定结论、条件结论、待校验结论。

每份报告生成后：

1. 等待用户反馈。
2. 记录命中点和偏差点。
3. 更新案例库。
4. 更新规则权重。
5. 下次同类报告自动避开已知错误。

## 八、阶段路线

### P0：架构与字段

- 完成数据库 schema。
- 完成来源登记。
- 完成规则评价表。
- 完成质量分级。

### P1：10万公开人物索引

- 用开放结构化数据建立小规模样本。
- 先验证管线，不追求数量。

### P2：100万三柱样本

- 开始做宏观分布。
- 形成第一版偏差矩阵。

### P3：1000万公开人物索引

- 采用批处理和去重。
- 不把全部样本视为高精度命例。

### P4：10万事件样本

- 抽取事件。
- 做大运阶段与人生事件关联。

### P5：1万高精度样本

- 人工审核出生时辰。
- 用于精细模块校验。

## 九、成功标准

系统不是以“数据量达到 1000 万”为成功，而以这些指标为成功：

- 每条规则有置信度。
- 每个结论有证据层级。
- 每份报告有个体化变量。
- 每个错误能回写。
- 每次生日或时辰修正能自动废弃旧判断。
- 报告能指出最该纠偏的现实行为。
